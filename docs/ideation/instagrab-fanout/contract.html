The problem

01instagrab today is a one-shot CLI that scrapes a flat list of Instagram usernames and writes JSONL. The user is building a separate website UI (any language, on their home lab) that needs to show a wall of recent images from the people one seed profile follows — and it needs to drive the scraper on demand, per friend, not just read a nightly file. The current binary can't be called from another process, only run.

02Two capabilities are missing outright. First, the code reads only follower/following counts, never the actual member list, so there is no way to discover who to fan out over. Second, that member list can only come from Instagram's private friendship endpoints, which 2025-26 enforcement treats as a top ban trigger — and the whole project's design ethos is to protect a real logged-in account. The design must add friends-list discovery and per-friend fan-out without turning normal runs into the exact request pattern that gets accounts suspended, and without letting account safety depend on an out-of-scope caller pacing its own loop.

Goals ×7
01 Expose instagrab as a C-ABI library so a web service in any language can drive it over FFI: a caller can connect, scrape one username, receive valid JSON, free it, and disconnect without crashing.
02 A normal fan-out run makes zero calls to the friendship endpoints — only web_profile_info and the post feed — producing one JSON result per reachable friend with posts limited to the rolling last-N-days window.
03 Provide friends-list discovery as a separate, off-by-default harvest call that pages the seed's Following once at human pace and returns the usernames; persisting them is the consumer's job.
04 Flag carousels and videos in each post's output (media_count, has_video) so the UI can badge a post and link out to Instagram, while only the first image is downloaded.
05 Make the FFI boundary panic-safe: any error crosses as an error JSON payload, never as a process-aborting panic.
06 Enforce a minimum inter-scrape pacing floor inside the library so a naive caller loop cannot exceed a safe request rate — account safety lives in the brain, not the caller.
07 Preserve the existing CLI's cron behavior and exit-code contract (0 OK, 1 config, 2 logged_out, 3 schema_drift, 4 browser, 5 canary_failed), now built on top of the library.

MVP — must ship ×9
  • Post output gains media_count / is_carousel / has_video flags; first image still the only download— Directly serves the 'tell me if there's more, I'll go to IG' decision and is a small additive parser change
  • src/harvest.rs: a dedicated module that pages the seed's Following once via the attached Chrome, parses the friendship page, and returns the usernames — the ONLY file referencing the friendship endpoint— The only sanctioned-by-design way to discover the fan-out set (goal #3), quarantined so the ban-trigger code is a single-file lexical guard
  • Consumer-side cache: harvest returns the list; the CLI persists it to a file and its fan-out mode reads it back (the library stays stateless between calls)— Gives the cache a named reader while honoring decision #5 — persistence is a consumer concern, not library state
  • CLI gains a fan-out mode that reads the cached friends list instead of config.usernames— Makes the CLI a real consumer of the cache and the home-lab cron path for the fan-out
  • Session enforces a minimum inter-scrape pacing floor (safe default, configurable)— Account safety must not depend on the out-of-scope website pacing its own loop; the floor keeps a naive caller under a safe rate
  • Public Rust library API (Session connect / harvest / scrape_one / disconnect) extracted from main.rs, with an explicit idle timeout and reconnectable dropped-connection errors— The library is the whole point; the FFI layer wraps it, and caller-driven gaps between calls can be unbounded
  • C-ABI FFI layer: extern "C" over an opaque handle, JSON in/out, catch_unwind, free_string, and a hand-written checked-in C header (include/instagrab.h)— Goal #1 — callable from any language; a hand-written header is the minimum-viable artifact for ~6 functions
  • CLI rewritten as a thin consumer of the library, preserving exit codes + JSONL + canary + jitter— Goal #7 — cron keeps working
  • scripts/ffi-smoke: a non-Rust caller exercising the FFI lifecycle offline (no live Instagram)— Proves goal #1 mechanically without spending cookie-jar risk on every verification
Full — target outcome ×3
  • cbindgen-automated header generation wired into the build— Keeps the C header in sync with the Rust FFI signatures instead of hand-editing
  • Structured error JSON with a machine-readable code enum across the FFI boundary— Lets the calling UI distinguish logged_out / not_found / network / stale-session without string matching
  • Release pipeline emits the Linux .so (x86_64-unknown-linux-gnu) for the home-lab deploy target— The current scripts/release cross-compiles a static musl binary and can't emit a loadable library
Out of scope — said no on purpose
  • The website / UI itself — Separate project in the user's chosen language; instagrab is only the brain
  • An HTTP / daemon layer — User will FFI directly; no network service needed
  • Downloading full carousels or video files — User prefers to click through to Instagram; keeps home-lab storage/bandwidth small
  • Harvesting the friends list on every run — That per-run pagination is exactly the ban fingerprint the design avoids
  • Using Instagram's official Graph API — It does not return follower/following member lists for any account
Future — someday, maybe
  • Convenience batch FFI call that loops the cached list internally for headless/cron callers (deferred; granular remains the primary surface)
  • Prune downloaded images that fall outside the rolling window
  • Harvest mutuals or followers (not just Following)
  • Opt-in per-run harvest for users who accept the risk
Decisions considered and rejected ×8
  • Discover friends via a cached list on disk, (re)built by a rare, explicit, off-by-default harvest— rejected: Auto-fetching the Following list on every run (or hand-typing usernames only). Instagram's friendship endpoints are the top ban trigger under 2025-26 enforcement; the followers dialog is just a UI over the same endpoint, so safety comes from rarity and human pacing, not from DOM-vs-endpoint. A cached list keeps normal runs off the endpoint entirely.
  • Ship instagrab as a C-ABI FFI library callable from any language— rejected: A Rust-only web service, or a long-running HTTP daemon. The user wants to FFI into the brain from a web service written in any language, keeping the site's language independent of Rust.
  • Download only the first image per post, but flag carousels and videos in the output— rejected: Downloading every carousel image and/or the video files. The user prefers to open Instagram directly for the full set; flagging keeps storage and bandwidth on the home lab small.
  • Apply a rolling last-N-days window per friend, reusing the existing time_window_days— rejected: A fixed [start, end] date range, or latest-page-only with no time filter. Matches the user's 'images for a set of time' and is already implemented per-profile in parse.rs.
  • Expose granular, caller-driven FFI calls as the primary surface; the library stays stateless between calls and the caller owns the loop and resume— rejected: A single batch call as the primary surface (a convenience batch call is deferred to future, not permanently rejected). Granular calls give the UI per-friend progress and survive restarts, and they push fan-out loop state into the web service where it belongs.
  • Enforce a minimum inter-scrape pacing floor inside the library (Session-level)— rejected: Relying on the existing CLI jitter or on the out-of-scope caller to pace its own loop. Critic fix (hidden-dependency blocker): the existing jitter lives only in the CLI loop, but decision #5 hands the loop to the out-of-scope website — a naive UI loop would hammer IG at full speed. Putting the floor in the library keeps account safety in the brain regardless of caller behavior.
  • Isolate the friendship-endpoint fetch in a dedicated src/harvest.rs module— rejected: Adding harvest_following alongside the feed fetch in src/scraper.rs. Critic fix (success-criteria blocker): quarantining the endpoint literal to one file makes the 'normal runs never touch the friendship endpoint' guarantee a single-file lexical check (grep -rl), which a shared module could not provide.
  • Keep all contract verification offline; the live FFI smoke against Instagram is a manual, deliberate dev step— rejected: Making a live canary scrape a top-level pass/fail success criterion. Critic fix (hidden-dependency + scope-creep blockers): CLAUDE.md forbids integration tests against live IG because every run costs cookie-jar risk; an offline lifecycle smoke proves the FFI boundary without spending that risk on every verification.
